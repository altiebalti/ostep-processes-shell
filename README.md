# wish — Unix-shell

Реалізація командного інтерпретатора **wish** (Wisconsin Shell) — лабораторна робота
за курсом операційних систем, проєкт [`processes-shell`](https://github.com/remzi-arpacidusseau/ostep-projects/tree/master/processes-shell)
з книги [OSTEP](https://pages.cs.wisc.edu/~remzi/OSTEP/).

Написано на C з використанням лише системних викликів: `fork`, `execv`, `wait`,
`chdir`, `access`, `open`, `dup2`. Виклик `system()` і `execvp()` не використовуються —
пошук програми в шляху виконується вручну.

**Результат: 22/22 автотести проходять**, збірка чиста під `-Wall -Werror`,
valgrind без помилок і без втрат пам'яті.

## Умова

Написати shell, який працює у двох режимах:

| Режим | Запуск | Поведінка |
|---|---|---|
| Інтерактивний | `./wish` | виводить запит `wish> `, читає команди зі stdin |
| Пакетний | `./wish batch.txt` | читає команди з файлу, **запит не виводить** |

Вимоги до функціоналу:

- вбудовані команди `exit`, `cd`, `path`;
- запуск зовнішніх програм з пошуком у списку каталогів (початково `/bin`);
- перенаправлення виводу `command > file` — і stdout, і stderr;
- паралельний запуск `cmd1 & cmd2 & cmd3`;
- єдине повідомлення про помилку `An error has occurred` у stderr.

## Швидкий старт

Проєкт збирається й запускається в Docker-контейнері з Debian 12, тому
результат однаковий на будь-якій хост-системі (macOS, Windows, Linux).

```bash
git clone https://github.com/altiebalti/ostep-processes-shell.git
cd ostep-processes-shell

./dev.sh make test    # зібрати та прогнати всі 22 тести
./dev.sh              # інтерактивна оболонка всередині контейнера
```

Всередині контейнера:

```bash
make                  # зібрати wish
./wish                # запустити
./test-wish.sh -c     # усі тести, не спиняючись на першій помилці
./test-wish.sh -v -t 22   # один тест з описом
```

Приклад сеансу:

```
wish> ls
Makefile  README.md  test-wish.sh  tests  wish  wish.c
wish> path /bin /usr/bin
wish> which gcc
/usr/bin/gcc
wish> cd /tmp
wish> pwd
/tmp
wish> ls > out.txt
wish> sleep 3 & echo instant
instant
wish> exit
```

> **Важливо:** не збирати проєкт напряму на macOS. Бінарник `wish` — це ELF для
> Linux, на macOS він не запуститься (`exec format error`). Завжди через `./dev.sh`.

## Як це працює

Обробка одного рядка введення:

```
getline()   "p1.sh > out.txt & p2.sh"
                        │
     strsep на '&'      │   розбиття на окремі команди
                        ├───────────────────┬──────────────
                        ▼                   ▼
             "p1.sh > out.txt"          " p2.sh"
                        │
     strsep на '>'      │   відділення файлу перенаправлення
                        ├───────────┐
                        ▼           ▼
                    "p1.sh"     " out.txt"
                        │
     tokenize()         │   розбиття на аргументи
                        ▼
                argv = { "p1.sh", NULL }
                        │
         вбудована? ────┴──── ні ──► fork()
              │                        │
              │                        ├─ [дитина]  open() → dup2() → execv()
             так                       └─ [батько]  продовжує запускати наступні
              │
              ▼
     виконати в батьку (без fork)


        ▼ після запуску ВСІХ команд рядка
    wait() × кількість дітей
```

Розподіл обов'язків у коді (`processes-shell/wish.c`, 230 рядків):

| Функція | Що робить |
|---|---|
| `main` | вибір режиму, цикл читання рядків через `getline` |
| `run_line` | розбиває рядок на команди по `&`, запускає всі, потім чекає всіх |
| `run_command` | відділяє `> file`, виконує вбудовані команди, інакше `fork` + `execv` |
| `tokenize` | розбиття на аргументи по пробілах, схлопуючи повтори |
| `path_resolve` | пошук програми в каталогах через `access(X_OK)` |
| `path_set` | заміна списку каталогів (вбудована команда `path`) |

## Ключові рішення

### Розбиття рядка через `strsep` по символах, а не по словах

`strsep` розділяє рядок за набором **символів**, тому оператори `&` і `>`
розпізнаються навіть без пробілів навколо них. Це прибирає потребу в
попередній обробці рядка:

```c
while ((segment = strsep(&rest, "&")) != NULL)   // wish.c:186
```

Завдяки цьому `p1.sh&p2.sh&p3.sh` (тест 19) і `ls tests>out` (тест 11)
працюють без окремих перевірок.

### Перевірки перенаправлення зводяться до підрахунку

Два послідовні виклики `strsep(&segment, ">")` (`wish.c:92-93`) залишають
`segment` непустим лише тоді, коли в рядку був **другий** `>`. А кількість
слів після `>` мусить бути рівно одна:

| Ввід | Слів після `>` | Результат |
|---|---|---|
| `ls > out` | 1 | ✅ коректно |
| `ls >` | 0 | ❌ файл не вказано (тест 8) |
| `ls > a b` | 2 | ❌ кілька файлів (тест 9) |
| `ls > a > b` | — | ❌ другий `>` (тест 10) |
| `> out` | 1, але немає команди | ❌ (тест 12) |

Порожній сегмент помилкою **не** є — тому одинокий `&` (тест 16),
завершальний `&` (тест 17) і порожні рядки (тест 21) обробляються мовчки.

### `open()` і `dup2()` викликаються в дитині, після `fork`

```c
pid = fork();                                        // wish.c:151
if (pid == 0) {
    int fd = open(outfile, O_WRONLY|O_CREAT|O_TRUNC, 0644);  // :160
    dup2(fd, STDOUT_FILENO);                                 // :165
    dup2(fd, STDERR_FILENO);                                 // :166
    close(fd);
    execv(program, argv);                                    // :169
}
```

Це найважливіше місце в роботі. Проміжок між `fork` і `execv` — єдиний
момент, коли процес уже новий, але ще виконує наш код. Саме тут
підміняються дескриптори 0/1/2. Програма `ls` про перенаправлення нічого
не знає — вона просто пише в дескриптор 1, який shell заздалегідь
переспрямував у файл.

Розташування `open()` саме в дитині принципове: два `open()` того самого
файлу створюють **два незалежні описи файлу з власними позиціями**. Якби
файл відкривався в батьку до `fork`, опис був би спільний — і тест 22 дав
би інший результат.

### Вбудовані команди виконуються в батьківському процесі

`cd`, `exit` і `path` не форкаються (`wish.c:127-136`). Робочий каталог —
атрибут процесу, тому `chdir()` у дитині зник би разом з нею:

```
$ pwd
/work/processes-shell
$ ( cd /tmp ; pwd )      # дужки = дочірній процес
/tmp
$ pwd
/work/processes-shell    ← батько не зрушив
```

З цього ж випливає вимога специфікації: перенаправлення до вбудованих
команд не застосовується.

### Пошук у шляху виконується вручну

`execv` вимагає повний шлях і сама нічого не шукає. Весь механізм «команда
знайдена» — це цикл перебору каталогів (`wish.c:47-56`):

```c
snprintf(full, len, "%s/%s", search_path[i], cmd);
if (access(full, X_OK) == 0)
    return full;
```

Тому `path` без аргументів робить список порожнім, і після цього перестає
працювати будь-яка зовнішня програма, включно з `echo` — саме це перевіряє
тест 7.

### `fflush(NULL)` перед `fork`, `write()` для помилок

`printf` пише в буфер у пам'яті процесу. При `fork` буфер копіюється, і
невиведений текст надрукувався б двічі — з батька й з дитини. Тому перед
розгалуженням буфер зливається (`wish.c:150`).

Повідомлення про помилки виводяться прямим системним викликом `write()`, а
не через `fprintf`, — без буферизації, тому порядок stdout і stderr
передбачуваний. Це критично для пакетного режиму, де харнес порівнює обидва
потоки окремо.

### Запустити всіх, потім чекати всіх

```c
while ((segment = strsep(&rest, "&")) != NULL)
    children += run_command(segment);     // запуск усіх

while (children-- > 0)
    wait(NULL);                           // і лише потім очікування
```

Порядок саме такий. Якби `wait` стояв усередині першого циклу, команди
виконувалися б послідовно — це ловлять тести 18, 20 і 22.

## Обробка помилок

Усі помилки виводять **єдине** повідомлення у stderr, байт у байт:

```c
char error_message[30] = "An error has occurred\n";
write(STDERR_FILENO, error_message, strlen(error_message));
```

Після помилки shell продовжує роботу. Винятки — вихід з кодом 1:

- передано більше одного аргументу командного рядка (тест 13);
- пакетний файл не відкривається (тест 14).

Перелік ситуацій, що вважаються помилкою:

| Ситуація | Приклад |
|---|---|
| `cd` без аргументів або з двома | `cd`, `cd /a /b` |
| `chdir()` не вдався | `cd /no/such/dir` |
| `exit` з аргументом | `exit 1` |
| програму не знайдено в шляху | `nonexistent` |
| помилки перенаправлення | `ls >`, `ls > a b`, `ls > a > b`, `> a` |

Перевірка, що shell не падає:

```
$ printf 'cd\nexit abc\nls > a b\ncd /nope\nnema_takoi\necho ALIVE\nexit\n' | ./wish
An error has occurred      ← ×5
...
ALIVE                      ← shell працює далі
```

## Тестування

### Автотести

```
$ ./dev.sh make test
test 1: passed
test 2: passed
...
test 22: passed
```

22 тести з апстрім-репозиторію. Кожен порівнює **три** речі окремо:
stdout (`.out`), stderr (`.err`) і код виходу (`.rc`).

| Тести | Що перевіряють |
|---|---|
| 1, 2 | `cd` з неправильною кількістю аргументів |
| 3, 4 | запуск зовнішніх програм, робочий каталог |
| 5 | `exit` з аргументом |
| 6, 7 | пошук у шляху, очищення шляху |
| 8–12 | перенаправлення та його чотири помилкові форми |
| 13, 14 | аргументи командного рядка, зіпсований пакетний файл |
| 15, 21 | пробіли, табуляції, порожні рядки |
| 16–20, 22 | паралельне виконання |

### Перевірка паралельності за часом

Найнадійніший спосіб довести, що команди справді виконуються одночасно:

```
$ time (printf 'sleep 3 & sleep 3 & sleep 3\nexit\n' | ./wish)
real  0m3.005s        ← три паузи по 3 с уклалися в 3 с, а не в 9
```

Зворотна перевірка — команди в **різних** рядках мусять бути послідовними:

```
$ time (printf 'sleep 1\nsleep 1\nsleep 1\nexit\n' | ./wish)
real  0m3.014s        ← правильно: shell чекає завершення кожного рядка
```

### Про оточення

| | Хост | Контейнер |
|---|---|---|
| ОС | macOS (Darwin, arm64) | Debian 12, Linux 6.12 (aarch64) |
| Компілятор | — | gcc 12.2 |
| libc | BSD | glibc 2.36 |

Каталог проєкту змонтований у контейнер як `/work`, тому редагувати код
можна на хості — контейнер бачить зміни одразу, перезбирати образ не треба.

Причина використання Linux, а не macOS: тест 3 дослівно порівнює текст
повідомлення `ls` про неіснуючий файл, а він відрізняється між BSD- та
GNU-версіями утиліти. Крім того, завдання написане під Linux і розраховує
на поведінку glibc.
